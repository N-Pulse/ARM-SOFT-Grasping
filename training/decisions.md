# Decision log — training/

One entry per decision. Newest at the bottom. Add an entry whenever a choice
would surprise someone reading the code later.

| date | decision | alternatives considered | reason |
|---|---|---|---|
| 2026-10-10 | **Object detection** (boxes), not instance segmentation | YOLO-seg; keep HSV segmentation + classifier | Goal is colour-independent, multi-object recognition. Boxes are enough to crop the depth cloud for `armsoft`; box labels are much cheaper (in-house set too); detection models are smaller and faster on the UNO Q CPU. Revisit if box crops include too much table/background in the point cloud. |
| 2026-10-10 | **YOLO26n**, fine-tuned from COCO weights | YOLOv8n/YOLO11n (detect), SSD-MobileNet, larger YOLO26s | Smallest current Ultralytics detector, NMS-free head (simpler export), ONNX/TFLite export supported. COCO pretraining already knows bottles and sports balls. "n" size for the ARM CPU budget. |
| 2026-10-10 | Start from an **Open Images V7 subset** (Ball, Tin can, Box, Bottle; ~500 img/class) | wait for the in-house D405 set; COCO (no can/box classes); synthetic renders | The in-house set is not ready. OI V7 has all four classes with boxes and a free licence. The dataset is behind `data.yaml`, so swapping to the D405 set is a one-flag change. Known gap: web photos ≠ D405 table scenes. |
| 2026-10-10 | **imgsz 416, CPU defaults** (device cpu, batch 16, workers 2, 30 epochs, patience 10) | 640 (Ultralytics default); GPU training | Training must run on a laptop CPU in hours, not days. 416 is also closer to the inference cost we can afford on the UNO Q. Objects at 30–70 cm on the D405 at 640x480 are not tiny. 640 is the first lever if small-object recall is low. |
| 2026-10-10 | **All iteration decisions use val** (next change, stop at val mAP50 ≥ 0.6, best model). Test is evaluated every iteration **for information only**; the final test numbers are those of the best-on-val iteration | select on test mAP50; evaluate test only once | Choosing by test score leaks the test set into model selection and inflates the reported number. Recording test per iteration shows the val/test gap without being used to choose. |
| 2026-10-10 | **Skip** Open Images detections with **IsGroupOf=True** or **IsDepiction=True** (box not written, image kept) | keep them; drop the whole image for group-of | A group-of box spans several objects, not one graspable instance; a depiction (drawing, poster, printed bottle) is not graspable. Trade-off accepted: the real objects inside a skipped group-of box stay unlabeled in that image. Counts are logged in `stats.json`; revisit (drop those images) if many images are affected. |

One less environment to maintain. WSL cannot see the USB camera. A fresh venv with `training/requirements.txt` also works (README). |

Time is better spent on the in-house D405 dataset than on tuning for web photos. |
| 2026-10-10 | Unit tests only where a bug would silently corrupt data or numbers: `yolo_format.py` and the evaluations.csv append | test every helper | One-week scope. The rest is thin glue around Ultralytics / FiftyOne / pyrealsense2, checked by smoke runs. |
| 2026-10-10 | Download Open Images from a **separate venv** `training/.venv-download/` (git-ignored, fiftyone + pyyaml only); training/eval/live tests stay in `.venv-win` | `pip install fiftyone` into `.venv-win`; `--no-deps` install | fiftyone depends on `opencv-python-headless` 4.14, which would overwrite `.venv-win`'s `opencv-python` 5.0 `cv2` and remove `cv2.imshow` (needed by `live_test.py`). | 2026-10-10 | **Known domain gap on `ball`**: Open Images ball boxes are tiny (train: median 0.4% of the image, 65% of boxes < 1% of the image area, mostly sports scenes), whereas a ball 30–70 cm from the D405 fills a large part of the frame. Expect a weak ball AP and a gap between test metrics and live tests. Candidate ONE change for iter2, decided on **val** only: drop ball boxes < 1% of the image area, or `imgsz 640` | keep as is; add more ball labels (Football, Tennis ball, …: also sports scenes) | Measured on the downloaded dataset (`training/datasets/openimages4/labels/train`). The two candidates attack different causes (tiny-object noise vs resolution); val per-class AP and the size breakdown decide which. |
| 2026-10-10 | **Known label noise**: 7 objects are labelled both `can` and `bottle` (two boxes, IoU > 0.7; 4 images in train, 3 in test). Kept as is (too few to matter), but counted when reading can↔bottle confusions. Some `box` labels are debatable (e.g. a metal pot, a strawberry-shaped tin) | remove the duplicates | Open Images annotation noise; changing test labels would break comparability with the raw subset. |
| 2026-10-10 | **Train on Google Colab (free T4 GPU)**, evaluate **always locally** (`eval.py` on the dev PC, `--notes "trained on Colab T4"`). Code and data go to Colab as **separate zips**: `training_code.zip` (re-made after each code change, small) and one zip per dataset in `MyDrive/npulse/data/` (uploaded once) | train on the laptop CPU (~1 h/run at imgsz 416, ~2.5 h at 640); evaluate on Colab; one zip with code + data | GPU makes each iteration minutes instead of hours (more room for the imgsz 640 candidate). Separate zips avoid re-uploading 550 MB of images for a code change, and let the in-house D405 dataset be added as its own zip. GPU and CPU training are not bit-identical, so the training machine is noted in each row. |
| 2026-10-10 | For the later `armsoft` integration, map **can, bottle → cylinder; box → cuboid; ball → sphere** | retrain a separate shape classifier; keep cylinder/cuboid only | `armsoft`'s grasp geometry works per shape primitive. The class→shape mapping keeps the existing cylinder/cuboid fit and grasp code. `sphere` is new and will need a fitter in `armsoft/core/shape_fitter.py` (integration task, not this week). |
| 2026-11-01 | **Compare models on all six required classes**: new `openimages6` dataset adds Pen→pen_pencil and Door handle→door_handle (IDs 4, 5; IDs 0-3 unchanged). `data.yaml`/`openimages4` stay as they were for iter1 | compare on the 4-class set; wait for the in-house D405 set | CV-REQ-002 requires six classes, and thin or small objects are where models may differ most. | 2026-11-01 | **Build `openimages6_far`** (same frozen source images assembled into 640x480 grids) to train and evaluate at the apparent object size of 50 cm-1 m. This **replaces the idea of dropping boxes < 1 % of the image** | drop small boxes; shrink each image on a grey canvas | Corrects the 2026-10-10 size assumption, written for 30-70 cm. At 50 cm-1 m, computed with the nominal 87° D405 field of view and typical object sizes, objects cover about 0.05-2.2 % of the image, while Open Images medians reach 13.9 % for can and 6 % for bottle and pen (val). Dropping small boxes would remove the useful sizes. A grey canvas was rejected after preview: isolated photos on grey are an artefact the model could learn. A pen at 1 m is about 2 px wide at imgsz 416, so imgsz 640 stays an important lever. This simulates scale only: the images are still web photos. |
| 2026-11-01 | **First D405 dataset** from the Dataset Studio session export (`DouaaKDR/Npulse`, revision `ac4f808`): approved frames only, classes matched **by name** (can, box, ball-pen→pen_pencil), split by whole session. Session metadata gives fx ≈ 393 px at 640x480, so object areas at 50 cm-1 m are about 1.36 times the earlier estimate (0.07-3 %), which does not change the conclusion. |
